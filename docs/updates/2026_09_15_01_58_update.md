# 2026-09-15 01:58 — Resume UI vs. the 10–30 s same-user refusal (web + Android)

Follow-up to the 01:18 Carbon 3 fix in `GameRoomService::requestResume`. A
same-user retry between 10 s and the 30 s expiry is now **refused**:

- `POST websocket/games/{id}/resume-request` → HTTP **200**
  `{ success: false, is_same_user: true, expires_in_seconds: <int>, message: "Your resume request is still pending…" }`
- `POST websocket/games/{id}/request-resume` (web HTTP fallback) → HTTP **409**
  `{ pending: true, requested_by_id, can_request_again_in_seconds }` (the controller checks before calling the service)

The refusal happens after a reload, from a second tab, or from the other
client (e.g. asked on Android, retried on web). The same tab can't reach it,
because the web's 60 s manual cooldown and the "sent" panel stop it first.

## What the clients did (checked, both wrong)

| Client | Before |
|---|---|
| Web, WS path | `WebSocketGameService.requestResume` throws with `fullData`. The message says "still pending", not "already pending", so `sendResumeRequest` took the generic branch: a red error toast and `{success:false}`. `handleRequestResume` had already set `isWaitingForResumeResponse = true` and returned without resetting it. The button stayed on "Requesting…" (disabled) with no countdown and nothing to reset it. Its `fullData`/`is_same_user` countdown code sits in a catch that never runs, because `sendResumeRequest` doesn't throw. |
| Web, REST 409 | The message contains "already pending", so it did a status fetch and then showed the "sent" panel with a made-up 10 s countdown instead of the server's remaining time |
| Android | `apiCall` treats any 2xx as success, so the 200 `success:false` showed **"Resume request sent"**. There was no pending state, and the button stayed live, so every tap sent another refused request |

## Changes

- **Web**: new `src/utils/resumeRequestRefusal.js` (`ownPendingResumeSeconds`).
  It recognises both refusal shapes (`is_same_user`, or 409 `pending` plus
  `requested_by_id === user.id`) and reads the remaining whole seconds.
  `PlayMultiplayer.sendResumeRequest` checks it first. The panel then shows
  "Resume request sent to opponent!" with the server's countdown (Cancel still
  available), clears the error, and returns `{ success:false, pending:true }`.
  `handleRequestResume` now resets `isWaitingForResumeResponse` on a
  non-pending failure, so a real error re-enables the button. The existing
  "already pending" fallback that shows the sent panel also returns
  `pending:true`. The opponent-pending path (status fetch, then the received
  panel) is unchanged.
- **Android**: `PlayMultiplayerViewModel.requestResumeGame` reads `success`.
  - A same-user refusal starts a countdown from `expires_in_seconds` and shows
    the snackbar "Your resume request is still pending. Waiting for your opponent."
  - An opponent-pending refusal says to accept the opponent's request.
  - Any other refusal shows generic retry copy. Backend text isn't shown
    verbatim, following the kid-safe copy rule.
  - A real send starts the 30 s window (`RESUME_REQUEST_WINDOW_SECONDS`).
  - New UI state `resumeRequestSecondsLeft`. Taps during the countdown are
    ignored, and `GameResumed`, `GameEnded` and `onCleared` clear it.
  - `PausedOverlay` disables the button and shows "Waiting for opponent… Ns".
