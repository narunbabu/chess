# 2026-08-12 — Android test suite completed ahead of the 1.0 release

## Why

The native app was feature-complete against web parity (Cycles 8–11) but carried
only 8 JVM tests — chat-safety rules and deep links. Everything that makes the
app *a chess app* (the rules engine, the ELO model, the Play-vs-Computer loop)
and everything that makes it *the same product as chess99.com* was untested.
That is the wrong risk profile for a Play Store release, and it made a
physical-device pass an unbounded manual exercise.

## What changed

Tests only — no production code was modified.

| Suite | File | What it locks down |
|---|---|---|
| Rules | `engine/ChessGameRulesTest.kt` | Castling (all three illegal cases + rights forfeiture), en passant incl. the pinned/discovery case, under-promotion, the five draw conditions, undo fidelity, FEN round-trips, SAN disambiguation |
| Move generation | `engine/ChessGamePerftTest.kt` | Perft against the five published reference positions (startpos to depth 4, Kiwipete/endgame/promotion/middlegame to depth 3–4), plus make/undo symmetry over every legal move |
| ELO model | `engine/EloMoveSelectorTest.kt` | The web `COMPUTER_LEVEL_RATINGS` table, the centipawn budget, softmax weighting, the opening-protected blunder ramp, mate safety rails, MultiPV rank-order robustness |
| ELO in play | `engine/EloLadderSimulationTest.kt` + `engine/SimulatedOpponent.kt` | Bots at 400–3200 play **complete games** against each other through the production selector: a 2600 scores ≥75% against a 600, score rises with rating against a fixed 1200 opponent, average centipawn loss falls monotonically up the ladder, and every rating still finds mate in one |
| Play journey | `presentation/game/PlayComputerViewModelTest.kt` | The web PlayComputer journey end to end — casual/learning/rated undo budgets, illegal-move rejection, turn ownership, undo rules, resign, checkmate both ways, share payload, bot personas (load, select, server start, rated/learning payloads, offline fallback), kid-safe engine-failure copy |
| Web parity | `parity/WebParityMatrixTest.kt` | A route-by-route contract between `chess-frontend/src/App.js` and `Screen.kt`: 33 shipped journeys, 24 documented deliberate gaps, uniqueness, and parameterised route builders |
| Utilities | `engine/OpeningDetectionTest.kt`, `engine/CCTAnalyzerTest.kt`, `engine/StockfishEngineMappingTest.kt`, `data/api/JsonSafeTest.kt` | Opening-book parity, CCT warning ladder and arrow budget, difficulty→movetime/tier/undo tables, and the JSON hardening that fixed the obfuscated `I5.n cannot be cast to I5.q` crashes |
| On device | `androidTest/.../StockfishEngineInstrumentedTest.kt` | The one layer JVM tests cannot reach: the bundled Stockfish binary actually starts for this ABI, completes the UCI handshake, returns legal ELO-shaped moves at every tier and explicit rating, finds mate in one at 400, survives a 30-ply self-play game, and analyses a position for game review |

`SimulatedOpponent` deserves a note: it is test scaffolding that supplies only
what Stockfish supplies at runtime — a MultiPV list of legal moves with
centipawn scores. The move *choice*, the rating table and the rules are all
production code, so the ladder results are a real measurement of our ELO layer,
not of a toy engine.

## Gate results

```

:app:lintDebug              0 errors, 118 warnings  (pre-existing backlog)
:app:connectedDebugAndroidTest   9 tests, 0 failures  (Medium_Phone_API_36.1, x86_64)
cold start                  clean — onboarding renders, no fatal exceptions
```

Three of the new tests initially failed and all three were faults in the test
expectations, not the app: a mis-stated castling-rights FEN, a "pinned" knight
that was in fact blocked by its own d2 pawn, and a rook-disambiguation position
where the king blocked the second rook's path. **Perft passed on every reference
position on the first run** — the hand-rolled move generator is correct.

## Still open before release

- Run `:app:connectedDebugAndroidTest` on the **physical phone**. The emulator
  exercised the x86_64 Stockfish binary; the shipped app runs arm64-v8a and
  armeabi-v7a, and `StockfishBridge` execs a binary out of `nativeLibraryDir`,
  which is exactly the kind of thing that differs per ABI and per OEM.
- The remaining release-owner items (production `google-services.json`, Play App
  Signing SHA-256 into `assetlinks.json`, Data Safety / Families declarations)
  are unchanged — see `STATUS.md`.
- UI-level instrumented tests (Compose) are still absent. The ViewModel suite
  covers the Play-vs-Computer *logic*; a Hilt-backed Compose suite for the wider
  navigation surface is the natural next increment.
