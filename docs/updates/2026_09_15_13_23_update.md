# 2026-09-15 13:23 — Dropped-player follow-ups: the loss, the counts, and the UI

Closes the STATUS item *"Backend: dropped-player follow-ups"*, the successor to
the 06:35 work that introduced `championship_participants.dropped_at` /
`dropped_reason`.

## 1. The drop's forfeits now record the dropped player's loss

`CheckExpiredMatchesJob::dropPlayerFromChampionship()` walked the dropped
player's remaining matches, set `status`/`result_type`/`winner_id` on each, and
then called `addResultToStandings(..., $opponentId, 'win')` — the opponent's
win and nothing else. The dropped player's own standing never moved, so their
`losses` and `matches_played` stopped at whatever they were when the drop
happened and the forfeited matches simply vanished from their record.

It now uses `processPlayerForfeit($match, $playerId, $opponentId)`, the method
that already writes both sides of a forfeit, and falls back to a lone
`'loss'` for a bye row (`player2_id` NULL — nobody to credit the win to, but
the dropped player still loses the match they will never play).

Why it was not visible in the existing tests: a **Swiss** championship runs
`updateStandingsAfterForfeit()` → `StandingsCalculatorService::updateStandings()`,
which recomputes the whole table from the match rows and masks the missing
increment. Outside Swiss (`elimination_only`) these increments are the only
standings record there is, so the new tests use that format.

## 2. Participant counts exclude dropped players

Five paid-participant counts still included players who can no longer be
paired — the pairing services (`SwissPairingService`,
`EliminationBracketService`) already excluded them, so the counts and the
pairings disagreed:

| Site | Effect of counting a dropped player |
|---|---|
| `GenerateNextRoundJob::hasEnoughParticipants()` | a championship with one player left kept generating rounds |
| `GenerateNextRoundJob::hasEliminationWinner()` | bracket never "finished" |
| `MatchSchedulerService::hasEliminationWinner()` | same |
| `MatchSchedulerService::scheduleMatchesWithTimeWindows()` | scheduled a round for players who cannot be paired |
| `AutoGenerateRoundsCommand::hasEliminationWinner()` | same |

All five now chain `->notDropped()`.

`ChampionshipRoundProgressionService::hasEliminationWinner()` is deliberately
untouched: that one derives the winner from the final round's match rows, not
from a participant count, so a drop cannot skew it.

## 3. The drop is surfaced in the UI

**API.** No new field was needed on the participant rows —
`ChampionshipParticipant::$appends` already serialises `dropped`, and
`dropped_at` / `dropped_reason` are plain columns. `GET
/api/v1/championships/{id}/participants` additionally returns
`active_participants` and `dropped_participants` (additive; `total_participants`
is unchanged).

**Web** (`ChampionshipParticipants.jsx`, `Championship.css`):

- a `🚫 Withdrawn — <reason>` badge, a struck-through name and a dimmed card
  for any participant with `dropped` / `dropped_at`;
- two new roster counters, **Still In** and **Withdrawn** (the payment
  counters cannot show this — a dropped player stays registered and paid);
- two new filter options, *Still In Only* / *Withdrawn Only*;
- a `role="status"` notice when the **signed-in player is the one withdrawn**:
  nothing else on the page told them.
- the six repeated stat cards are now one `StatCard` with `role="group"` +
  `aria-label`, so each counter is nameable (and assertable) without DOM
  walking.

**Android** (`ChampionshipDetailScreen.kt`): `Participant` gained
`dropped` / `droppedReason`; the participants-tab row strikes the name through
and shows `Withdrawn — <reason>` in the error colour. The parser was lifted out
of the ViewModel into an internal `parseParticipants(JsonArray)` so it is unit
testable, and moved onto the null-safe `JsonSafe` helpers (the old body used
raw `asInt`/`asJsonObject` inside a `try`). It reads `dropped`, falling back to
`dropped_at != null`.
