## Decision: auto-pause IS wanted

- The owner-approved 18:31 lifecycle decision (docs/updates/2026_09_14_18_31_update.md)
  reads: "`games:monitor-inactivity` every minute pauses active games after ~70 s
  inactivity … so even a left-active game converges to paused → aborted." The command
  is deliberately scheduled `everyMinute()` in `bootstrap/app.php:25`.
- The web client already pauses client-side ("Are You There?" dialog →
  `WebSocketController::pauseGame`); the monitor is the fallback when the client is
  gone entirely (killed tab/crash). Pausing freezes the clocks
  (`*_time_paused_ms`), a returning player's heartbeat auto-resumes it
  (`GameRoomService::updateGameHeartbeat` resumes `paused_reason='inactivity'`),
  and `games/unfinished` lists it for Home/web resume; 1 h later
  `games:cleanup-abandoned` aborts it with `result='*'`.

## Second latent bug found while testing: signed Carbon 3 diffs

Even with the TypeError fixed, the pause and forfeit branches still never fired:
`Game::getInactiveSeconds()` / `getPausedSeconds()` used
`now()->diffInSeconds($past)`, which is **negative** under Carbon 3 (3.10.3 here)
because Carbon 3 diffs are signed by default. Verified in a debug run: a game idle
5 min reported `inactive=-300s`, so `>= 70` was never true. Fixed both helpers to
use `diffInSeconds(now(), true)` (absolute). These helpers are used only by this
command (`rg` confirmed), so the blast radius is the monitor itself.

## Changes

- `chess-backend/app/Services/GameRoomService.php` — `pauseGame()` now takes
  `?int $pausedByUserId = null`: a null pauser means a **system pause**
  (`paused_by_user_id` stays null — the column is nullable; `GamePausedEvent`
  already accepted `?User`, and its payload sends `paused_by_user_id: null`).
  Log/return fields are null-safe. The authenticated controller caller
  (`WebSocketController::pauseGame`) is unchanged.
- `chess-backend/app/Console/Commands/MonitorGameInactivity.php` —
  - the pause call is now `pauseGame($game->id, null, 'inactivity',
    $game->white_time_remaining_ms, $game->black_time_remaining_ms)`: a system
    pause that freezes the server's last known clocks instead of falling back to
    the 10-minute default;
  - the game query excludes bot games (`whereNull('computer_player_id')` +
    `whereNull('synthetic_player_id')`, the same "human game" idiom used by
    LobbyController/InvitationController). This excludes them from BOTH branches:
    pausing a bot game needs mutual resume consent no bot can give (the paused
    overlay only offers `requestResume`), and the forfeit path assumes two real
    players (for a synthetic game one player id is null — it previously crashed
    in `isUserOnline(null, ...)` and logged an error every minute). Bot games now
    deterministically follow the designed path: stay paused (or active) until
    `games:cleanup-abandoned` aborts them at 1 h with `result='*'`, never a loss.
    Rated bot games were never pausable anyway (`pauseGame` refuses rated).
- `chess-backend/app/Models/Game.php` — `getInactiveSeconds()` /
  `getPausedSeconds()` now return absolute diffs (Carbon 3 signed-diff fix).
- `chess-backend/tests/Feature/MonitorGameInactivityTest.php` — new, 7 tests:
  inactive human casual game auto-paused as a system pause (status/reason/null
  pauser/frozen clocks/40 s grace to the side to move/`GamePausedEvent` payload);
  recently-active game untouched; rated game never paused; synthetic bot game and
  plain computer game excluded (`Found 0 games to check`, still `active`);
  31-min-paused human game forfeited by timeout (branch still works);
  31-min-paused bot game left for the hourly cleanup (stays paused, `result
  'ongoing'`, no loss).
