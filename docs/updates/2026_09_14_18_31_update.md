# 2026-09-14 18:31 — Decision: Leave game must NOT end a casual bot game server-side

## Question

TODO item (STATUS.md): after Android "Leave game" the casual bot game (463) stayed
`ongoing` (`result='ongoing'`, status `active`) on the server. Should Leave resign or
abandon the game server-side, or is staying non-terminal correct?

## Answer

**Leave game should not end a casual bot game server-side.** At every layer the
platform treats leaving a casual game as *pause → resumable → expire with no result*,
never as a recorded loss. The observed "stayed ongoing" is non-terminal (correct
family), but two Android parity defects caused the confusion — see "What is actually
wrong" below. No code was changed by this decision.

## Evidence (code reading only; no runtime or production checks this session)

### Web reference client: casual leave = pause, never a loss

- Casual **bot** games on web (PlayComputer) persist a server game and, on
  navigation/beforeunload, `saveUnfinishedGame` calls
  `POST /games/{id}/pause-navigation`
  (`chess-frontend/src/services/unfinishedGameService.js:134`). The game becomes
  `paused`, not finished.
- Casual **multiplayer** leave: the navigation dialog offers only "Pause Game &
  Navigate" (`chess-frontend/src/components/game/GameNavigationWarningDialog.jsx`),
  handled in `chess-frontend/src/components/play/PlayMultiplayer.js:3195-3242` via
  `wsService.pauseGame`.
- Only **rated** leave forfeits: "Forfeit & Leave" sends `resignGame`
  (`PlayMultiplayer.js:3246-3328`); the rated dialog says it will count as a loss.
  So the Android copy "it counts as a loss" is the *rated* copy.

### Backend: the pause/resume machinery exists exactly because casual leave is not an end

- `GameController::pauseNavigation` (`chess-backend/app/Http/Controllers/GameController.php:1448`)
  pauses casual games; rated games are refused with 403 "Rated games cannot be paused"
  (line 1478). Same guard in `GameRoomService::pauseGame`
  (`chess-backend/app/Services/GameRoomService.php:1636`).
- `GET /games/unfinished` (`GameController.php:1368`) returns only `paused` games
  (reason navigation/inactivity/beforeunload, < 1 h) and auto-aborts stale ones to
  `aborted` / `result='*'`.
- A loss for a synthetic/bot game can only be recorded through explicit
  resign/complete (`GameController::resign` :1021, `completeGame` :582 — both write
  `game_history` and, for rated, Elo). Nothing in the designed leave path does that.

### Abandoned games self-heal to "no result", by design

- `games:cleanup-abandoned --skip-championship --paused-hours=1` hourly
  (`chess-backend/app/Console/Kernel.php:36`): 1+-move **active** games untouched for
  7 days → `aborted`, `result='*'`, timeout-inactivity; paused games expire after 1 h
  the same way. Never a loss.
- `games:monitor-inactivity` every minute (`chess-backend/bootstrap/app.php:25`)
  pauses active games after ~70 s inactivity (`config/game.php`), so even a
  left-active game converges to paused → aborted. (Monitor can forfeit *paused human*
  games at 30 min via `GameRoomService::forfeitByTimeout` :2371; for synthetic games
  one side has no User — runtime behaviour not verified here.)
- Caveat: whether the production VPS actually runs `php artisan schedule:run` was not
  re-verified this session; `chess-backend/setup_log_rotation.sh` installs that cron.

### Android current state (the defects, not the end-state)

- `onLeave` only navigates back — no server call for any game type
  (`chess99-android/app/src/main/java/com/chess99/presentation/game/PlayMultiplayerScreen.kt:100`).
  The game stays `active`, so it never enters `games/unfinished` (paused-only); it
  only lingers in `games/active` (Home "Continue playing", `HomeViewModel.kt:31`).
- `GameApi.pauseNavigation` is already declared and never called
  (`chess99-android/app/src/main/java/com/chess99/data/api/GameApi.kt:55`) — the
  parity step was planned but never wired.
- Dialog copy is one-size-fits-all: "If you leave now, it counts as a loss."
  (`GameNavigationWarningDialog.kt:43`) — false for casual games, and currently false
  even for rated because rated Leave also sends nothing.

## Decided follow-ups (implementation, not done here)

1. Casual Leave (incl. bot games): fire-and-forget `GameApi.pauseNavigation(gameId)`
   before navigating; change casual dialog copy to pause/resume wording (web parity).
2. Rated Leave: send the resign (reuse the `resign()` synthetic/complete path in
   `PlayMultiplayerViewModel.kt:660`) so "counts as a loss" becomes true server-side.
3. Optionally reflect resume state in the dialog (web casual copy mentions resuming).
